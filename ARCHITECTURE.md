# Architecture — Gudavalamma Temple Management Platform

> Read this first. It's written so an LLM (or a new engineer) can understand the whole system without crawling every file.

## What this app is

A temple management platform with two audiences sharing one codebase:

- **Devotees and guests** — browse and book darshan/seva/accommodation/prasadam, make donations, view announcements, all **without needing an account** (guest checkout — see below); logging in additionally gets you a persistent "my bookings" view. Public-facing entry point is `/`.
- **Staff** — log in separately, manage the temple's operational data: donors, properties, assets/liabilities, an Excel-like expense/event tracker, the catalogs that power the devotee side (seva list, darshan quotas, room types, prasadam items, donation funds, facilities, announcements, temple profile/social links), the enabled-languages list, and a drag-and-drop visual customizer for every devotee-facing screen.

Devotees and staff are **the same `User`/`Role` model** — there is no separate devotee schema. They're distinguished only by `Role.roleType` on the backend and by a client-side `audience: 'staff' | 'devotee'` tag stored in Redux at login time (see `Admin/src/types/auth.ts` for the comment explaining this).

## Tech stack

| Layer | Stack |
|---|---|
| Backend | Node.js, TypeScript, Express 4, Mongoose 8 (MongoDB) |
| Frontend | React 19, TypeScript, Vite, Redux Toolkit + RTK Query, redux-persist, react-router-dom 7, PrimeReact 10 (UI kit), react-hook-form + zod (forms), Tailwind (utility classes on newer pages) |
| Auth | JWT access/refresh tokens, stored server-side in a `Token` collection (not just stateless JWT — revocable) |
| i18n | Custom (not a library) — 3 bundled hand-written locales (English/Telugu/Hindi) plus 20 more on-demand via a translation engine (see below); backend `t()` in `server/src/i18n`, frontend `useStaffTranslation()`/`useDevoteeTranslation()` hooks backed by **independent** Redux `preferences.staffLocale`/`preferences.devoteeLocale` fields (persisted) — switching one audience's language never affects the other |
| Translation | Self-hosted **LibreTranslate** primary, **LLM fallback** (reuses the same `llmService` below) for any language pair LibreTranslate doesn't support — both free, no paid API |
| Drag-and-drop builder | `react-grid-layout` (v1.x API — the newer v2 has an incompatible hooks-based API, intentionally avoided) |
| Charting | `recharts` (for the staff Analytics page — see Phase 12 below; `chart.js` is also installed but unused, left over from the original template) |
| Scheduled jobs | `node-cron` (currently one job: the nightly analytics rollup — see below) |

## Backend structure (`server/`)

Every domain lives under `server/src/modules/<name>/` with a consistent file set:

```
<name>.model.ts       Mongoose schema + TS interface
<name>.schema.ts       zod validators for request body/params
<name>.service.ts      business logic, throws AppError on failure
<name>.controller.ts   sets req.entityType/req.<entity>, calls respUtil.*
<name>.route.ts         Express Router: authMiddleware -> permissionGuard -> validate -> asyncHandler
<name>.docs.ts          swagger-jsdoc comment blocks (optional)
```

All response shapes are `{ success, statusCode, respMessage, data, meta, errors }` (see `server/src/utils/resp.util.ts`). Routes are all mounted under one prefix (`API_PREFIX`, default `/api/v1`) via `server/src/routes/index.ts` — **that file is the single source of truth for what endpoints exist**.

### Modules

| Module | Purpose |

| `auth` | login (email+password *or* phone+password, Phase 18) /register/forgot-password/refresh-token, plus `POST /auth/otp/request` and `/auth/otp/verify` (devotee mobile-number OTP login, Phase 18 — public, phone-keyed rate limit). All three successful-login paths (`login`, `verifyOtp`) share one `issueSession()` helper for JWT issuance. |
| `user` | User CRUD, self-profile update (`PATCH /users/me`), locale update |
| `role` | Role CRUD; `Role.permissions` is a `Map<moduleKey, {type, actions[]}>` — this is the RBAC source of truth |
| `menu` | DB-driven sidebar nav (staff side); `GET /menus/my-menu` returns the tree filtered by the caller's role permissions |
| `settings` | generic key/value store (`group`/`key`/`value`), also holds the LLM provider/model override |
| `token`, `activity`, `tableView`, `upload` | generic infra (JWT storage, audit log, saved table views, file uploads) |
| `dashboard` | generic dashboard-config store (not the devotee home page — see Frontend below) |
| `booking` | **shared ledger**. Every darshan/seva/accommodation/prasadam/donation booking writes one row here (`{devotee, type, refId, refModel, title, amount, date, status, paymentStatus, paymentReference}`) via `bookingService.createLedgerEntry`. `GET /bookings`, `POST /bookings/:id/cancel`, `GET /bookings/:id/receipt` are devotee-scoped (self only, auth required). `GET /bookings/all` is a **staff-only, paginated, filterable** view across every devotee (permission key `bookingLedger`, `View`+`Update` — built in Phase 10b, `Update` added in Phase 15 for "mark as paid"), backed by `Booking.list()`/`.totalCount()` statics and `bookingService.applyQueryFilters` (`type`/`status`/`paymentStatus`/`from`/`to`). Cancel dispatches to a per-type handler registered via `booking.registry.ts`'s `registerBookingCancelHandler` — each domain module registers its own handler at import time. `PATCH /bookings/by-ref/:refId/payment-reference` (Phase 15) is the one **public, unauthenticated** route on this module — see Payments section below for why. `PATCH /bookings/:id/mark-paid` is staff-only. |
| `seva`, `darshan`, `accommodation`, `prasadam`, `donation` | catalog (staff-manageable) + booking/order (devotee-created) pairs. Catalogs auto-seed a default set of rows on first `GET` if the collection is empty. Each catalog model also has optional `bookingOpensAt`/`bookingClosesAt` (`"HH:mm"` strings, Phase 10e) — **informational only, not enforced server-side** — displayed on the matching devotee booking page via `Admin/src/utils/bookingHours.ts`'s `formatBookingHours()`. `donation` additionally has a staff-only, paginated `GET /donations` ledger (permission key `donation`, view-only, Phase 10b), separate from the staff-manageable `donationFund` catalog. |
| `facility` | static admin-managed content list (no booking) |
| `announcement` | `GET /announcements/active` is public (feeds the home-page popup); full CRUD is staff-only. `Announcement.linkedEventId` (Phase 10a) optionally points at a `TempleEvent`, so a festival announcement's popup can deep-link straight to that event's registration page. |
| `templeProfile` | singleton document — temple name/address/helpline/logo/social links, plus `timings: [{label, time}]`, `contactEmails: string[]` (Phase 10c), `upiId` (Phase 15 — the temple's own UPI VPA, used to build payment links/QR codes), and `nameTranslations: Record<locale, string>` (Phase 19 — auto-filled per-locale translation of `templeName`, regenerated whenever the English name changes since there's no manual per-locale edit UI for it). `GET` is public, `PUT` is staff-only. |
| `templeEvent` (+ its `eventRegistrationRouter`) | Phase 10a. `TempleEvent` (name/description/imageUrl/startDate/endDate/registrationRequired/capacity/registrationDeadline/active) — public `GET /temple-events`, staff CRUD, staff `GET /temple-events/:eventId/registrations`. `EventRegistration` (event ref + optional devotee or guestName/guestEmail/guestPhone, same guest-checkout shape as bookings) — `POST /event-registrations` is guest-checkout (`optionalAuthMiddleware`), `GET /event-registrations/mine` requires login. `register()` enforces `registrationDeadline` and `capacity` (counting non-cancelled registrations) and sends a confirmation email, but does **not** write to the shared `booking` ledger — registrations are tracked only in `EventRegistration`. |
| `nearbyPlace` | Phase 10d. Simple staff-managed catalog — `NearbyPlace` (name/description/distanceKm/imageUrl/category (`heritage`\|`nature`\|`shopping`\|`food`\|`accommodation`\|`other`)/mapLink/active). Public `GET /nearby-places` (unpaginated, active-only), staff CRUD. No booking/order side — it's pure informational content ("must-visit places near the temple"), each with an optional `mapLink` that becomes a "Get Directions" link on the devotee page. |
| `analytics` (`analyticsEvent` + `analyticsDailyRollup` models) | Phase 12. `AnalyticsEvent` is the raw log — `{sessionId, userId?, path, eventType: 'pageview'\|'click'\|'funnel_step', targetLabel?, funnelName?, stepIndex?, stepName?, timestamp}`. `POST /analytics/events` is **public** (`optionalAuthMiddleware`) and accepts a **batch** array — the devotee frontend's `trackEvent`-style helper (`Admin/src/utils/analytics.ts`) buffers events in memory and flushes every 10s or on tab-hide via `navigator.sendBeacon`, never one request per click. `AnalyticsDailyRollup` is one pre-aggregated document per UTC calendar day (`totalPageviews`/`totalClicks`/`uniqueSessions`/`topPages`/`topClicks`/`funnels`), computed nightly by `server/src/jobs/analyticsRollup.job.ts` (`node-cron`, `0 1 * * *`) and also staff-triggerable on demand via `POST /analytics/rollup/run`. Staff `GET /analytics/summary?days=30` (permission `analytics`) mixes both sources: the daily-visits trend reads the rollup (fast, pre-computed, with today's bucket computed live since it has no rollup yet); top pages/top clicks/funnel drop-off query raw `AnalyticsEvent` live for flexibility. The 6 funnels and the ~20 instrumented click-target labels are fixed lists in `analytics.constants.ts` (`FUNNEL_NAMES`, `INSTRUMENTED_CLICK_LABELS`) — not a generic funnel/event builder; adding a 7th tracked flow means adding a name to that list and a few `trackFunnelStep` calls on the frontend, by hand. |
| `templeReconfigure` | Phase 11. The "reconfigure this instance for a new temple" wizard's backend — **not a CRUD resource**, just two endpoints: `GET /temple-reconfigure/catalogs` (counts + `supportsDefaults` flag per catalog) and `POST /temple-reconfigure/reset-catalog` (`{catalog, mode: 'empty'\|'defaults'}` — hard-deletes every document in that catalog, then re-seeds from the catalog's own starter defaults if `mode==='defaults'` and the catalog has any). Deliberately **not added to any role except `SUPER_ADMIN`** in `roles.constants.ts` — there is no ADMIN/MANAGER path to this endpoint, by design, since it's destructive. Reuses each catalog's own pre-existing default-seed logic (`sevaService.listActive()`, `darshanService.listActive()`, etc. — see `templeReconfigure.service.ts`'s `CATALOG_REGISTRY`) rather than duplicating the DEFAULT_* arrays. |
| `donor`, `property`, `asset`, `liability` | staff-only record-keeping modules, no devotee-facing side |
| `expenseEvent`, `expenseEntry` | the "Excel-like" tracker: `ExpenseEvent` is an optional grouping (a festival/occasion); `ExpenseEntry` is a ledger row, income or expense, optionally tagged to an event. Bulk-create + summary aggregation endpoints exist for Excel import/export. |
| `language` | `Language` collection seeded with all 22 official Indian languages + English (`code`/`name`/`nativeName`/`enabled`/`isDefault`). `GET /languages/enabled` is public (feeds the switcher); enabling a language (`PUT /languages/:code`, staff-only) fires a background pass that pre-warms the translation cache for menu titles, announcements, and temple profile text. |
| `translation` (service, not a CRUD module) | `translationService.translateText(text, from, to)` — tries LibreTranslate first (checked against its `/languages` support list, cached in-process), falls back to `llmService.generateText` with a translation prompt on error or unsupported pair. Every result is cached in `TranslationCache` (unique on source-hash + locale pair) so nothing is translated twice. `POST /translations/:locale` lets the frontend translate its bundled English string dictionary into any non-bundled locale on first use. |
| `pageContent` | the drag-and-drop screen customizer's backend. One document per `screenKey` (`home`/`darshan`/`seva`/`accommodation`/`prasadam`/`donations`/`facilities`/`live`/`events`/`nearbyPlaces`) holding a `draft` and a `published` widget array, plus a capped `versions[]` history (Phase 14b). `GET /page-content/:screenKey` is public (serves `published`); `.../draft` GET/PUT, `.../publish` POST, `.../versions` GET, and `.../versions/:versionId/restore` POST are staff-only. Saving a widget's English text auto-fills every other enabled locale via `translationService`, without overwriting a locale an admin already edited by hand. Every Publish snapshots the newly-published widgets into `versions` (capped at 20); restoring a version copies it into `draft` only, never `published` directly. |

### Cross-cutting infra

- `server/src/middlewares/auth.middleware.ts` — verifies JWT against the `Token` collection (revocable, not pure stateless JWT), populates `req.user` with role.
- `server/src/middlewares/role.middleware.ts` — `permissionGuard(moduleKey, action)` checks `req.user.role.permissions.get(moduleKey).actions` includes `action`. `SUPER_ADMIN` always passes.
- `server/src/constants/roles.constants.ts` — `SEED_ROLES`, the canonical permission map per role, applied by the seed script. **Every module's permission key must appear here** for a role to access it via `permissionGuard`.
- `server/src/database/seeds/index.ts` — `npm run seed`. Upserts roles, calls `seedMenus()`, seeds LLM settings, seeds seva/darshan catalogs. **Idempotent** — safe to re-run; never touches the `users` collection.
- `server/src/database/seeds/menu.seed.ts` — the sidebar's `defaultMenus` array (title/route/permissionKey/iconName/submenu). A new staff screen needs an entry here (icon names must exist in `Admin/src/utils/menuIcons.ts`'s map or it silently falls back to a plain circle icon) **and** a matching permission key in `roles.constants.ts`, or it won't render/won't be accessible.
- `server/src/config/llm.config.ts` + `server/src/services/llm/llm.service.ts` — switchable LLM provider (`openai`|`ollama`), configured via `.env` (`LLM_*` vars) with a runtime override stored in `Settings` (group `llm`). No temple feature calls this directly, but `translationService` uses it as a fallback (see the `translation` module above) — this is the "real job" that infra ended up getting.
- `server/src/i18n/` — `en/`, `te/`, `hi/` folders, one file per module, merged in `server/src/i18n/index.ts`'s `translations` map. `req.locale` is negotiated from `Accept-Language` in `app.ts`. This covers backend-emitted messages only — UI string translation for non-bundled locales goes through the `translation` module instead (see above).
- `server/src/middlewares/optionalAuth.middleware.ts` — like `authMiddleware` but never rejects; populates `req.user` if a valid token is present, otherwise leaves the request to proceed as a guest. Used on the 6 booking/order/donation/registration-creation routes that support guest checkout (darshan/seva/accommodation/prasadam/donation/event-registration — see below) plus the public analytics-ingestion endpoint (so a logged-in devotee's clicks get tagged with their `userId`, without requiring one) — every other protected route still uses `authMiddleware`.
- `server/src/utils/guestCheckout.util.ts` — `resolveBooker(req, body, locale)`, called by each of the 5 booking controllers right after `optionalAuthMiddleware`. Returns the logged-in user's identity if present; otherwise requires `guestName` + at least one of `guestEmail`/`guestPhone` in the body and throws a 400 if missing. Every domain model (`DarshanBooking`, `SevaBooking`, `AccommodationBooking`, `PrasadamOrder`, `Donation`) has `devotee` as **optional** plus `guestName`/`guestEmail`/`guestPhone`/`preferredLocale` fields for this reason.
- `server/src/services/notification/bookingEmail.service.ts` — sends a booking/order/donation confirmation email (temple name, details, reference ID) translated to the booker's `preferredLocale` via `translationService`, using the existing `nodemailer` transporter (`server/src/utils/mail.util.ts`, `MAIL_*` env vars). Called fire-and-forget at the end of each booking-creation service method — a mail failure is logged, never fails the booking.
- `server/src/utils/service.util.ts`'s `generateListQuery(req, screenName)` — the generic list/filter/sort/paginate DSL used by every "rich" staff list screen. Its default filter is `{isDeleted: {$ne: true}, active: true}`; **models without an `active` field (the `Booking` ledger, `Donation`) must explicitly `delete query.filter.active` / `delete query.filter.isDeleted` after calling it**, or every row gets filtered out silently (see the Phase 10b entry in `MEMORY.md`'s incidents list). `buildFilterCriteria` supports date-range criteria types (`dategte`/`datelte`/`dateis`/etc.) generically — this is what both `CommonTable.tsx`'s per-column date filter and the `YearFilter` component (below) ultimately drive.
- `server/src/jobs/analyticsRollup.job.ts` — the app's one scheduled job (Phase 12), started from `server.ts` right after `connectDB()` via `startAnalyticsRollupCron()`. Runs nightly (`node-cron`, `0 1 * * *`) computing the previous day's `AnalyticsDailyRollup`. Re-registers on every `ts-node-dev` hot-reload in dev — harmless, `node-cron` doesn't stack duplicate schedules across a single process's lifetime, but a full process restart is still what actually re-arms it.

## Frontend structure (`Admin/`)

Despite the directory name, this single Vite app serves **both** the staff admin panel and the devotee portal — routing decides which shell renders.

### Routing (`Admin/src/routes/AppRouter.tsx` — read this file to see the whole site map)

- `/` — **public, adaptive home page**. Renders `DevoteeDashboardPage` inside `DevoteeLayout`, gated only by `HomeGate` (which redirects an authenticated *staff* user to `/dashboard`; everyone else — anonymous or a logged-in devotee — sees it). Anonymous visitors see a hero + login CTAs; logged-in devotees see their personalized dashboard (queue status, festival countdown, quick links). This is the "merged dashboard/home page."
- `/login`, `/forgot-password` — staff auth (`PublicOnlyRoute` bounces already-logged-in users away). No staff sidebar (can't render meaningfully pre-auth), but both pages have a minimal "← Back to temple site" link to `/` (Phase 17b) so a visitor who lands here isn't trapped.
- `/devotee/*` — **one shared `<DevoteeLayout>` wraps every devotee-side route**, including `login`/`register`/`forgot-password` (Phase 17a — previously these rendered standalone outside any layout, with no nav at all). `DevoteePublicOnlyRoute` is nested *inside* `DevoteeLayout`'s children, not a sibling branch, so the auth pages get the real `dp-header`/`dp-footer`/nav — the same header already correctly shows Login/Register CTAs instead of the authenticated menu when the visitor isn't signed in. `/devotee/dashboard` is a redirect to `/` (kept for old links/redirect-target compatibility, not a real page anymore). **Guest checkout**: `darshan`, `seva`, `accommodation`, `donations`, `prasadam`, `live`, `facilities`, `events`, `nearby-places` are public — no `DevoteeProtectedRoute` wrapper, so anonymous visitors can book/order/donate/register directly (each form shows inline name/email/phone fields via the shared `useGuestCheckout` hook + `GuestContactFields` component when not logged in). Only `bookings` (the "my bookings" ledger view) and `profile` stay behind `DevoteeProtectedRoute`, since those inherently require a persisted identity — there is no persistent guest account.
- Everything else (`/dashboard`, `/users`, `/roles`, `/settings`, `/profile`, and every Temple Management screen — including the Phase 10 additions `/events`, `/staff-donations`, `/staff-bookings`, `/nearby-places`) is behind `ProtectedRoute` + `AppLayout` (the staff shell — sidebar + header).

### Staff shell (`AppLayout` / `Sidebar` / `AppHeader`)

`Sidebar.tsx` renders nav **fetched live from the backend** (`GET /menus/my-menu`, see `Admin/src/services/api/endpoints/menusApi.ts`) — it is NOT a static route config. Adding a page to `AppRouter.tsx` makes it reachable by URL but does **not** make it appear in the sidebar; you also need the `menu.seed.ts` entry described above.

### The generic CRUD engine (`Admin/src/components/crud/CrudPage.tsx` + `CommonTable.tsx` + `CommonForm.tsx`)

Nearly every staff screen (Users, Roles, Donors, Properties, Assets, Liabilities, the catalog-management pages, Events, Nearby Places) is a thin wrapper: a `models/<x>Model.tsx` file (zod schema, form field config, table columns, payload mappers) + a `services/api/endpoints/<x>Api.ts` file (RTK Query `injectEndpoints`) + a one-line `pages/<X>Page.tsx` that renders `<CrudPage config={...} />`. **Read `Admin/CRUD_GUIDE.md` before building another one of these** — it documents the pattern in full.

Two flavors of `api.useListQuery`, depending on what the backend endpoint returns:
- **Paginated** (`{data, meta:{page,pageSize,total}}`) — the RTK Query hook takes a `CrudListQuery` and passes it straight through as query params/a `filter` JSON blob. Used by anything backed by `generateListQuery` (Users, Donors, and the Phase 10b staff ledgers).
- **Flat, unpaginated array** — several catalog-style endpoints (sevas, darshan quotas, room types, prasadam items, donation funds, facilities, announcements, temple events, nearby places) just return every active row. `Admin/src/utils/crudStaticList.ts`'s `toStaticCrudListResult(query, result)` adapts a plain `useGetXQuery(void)` hook into the shape `CrudPage` expects (client-side pagination/sort over the full list) — see `EventsPage.tsx`/`NearbyPlacesPage.tsx` for the `useXListQuery` wrapper pattern. Don't build a bespoke paginated backend endpoint for a catalog this small; use this adapter instead.

Two screens don't fit the CrudPage pattern at all:
- `ExpenseTrackerPage.tsx`, which uses a bespoke `EditableGrid.tsx` (PrimeReact `DataTable` with per-cell inline editors) because it needs spreadsheet-style editing, not modal-based CRUD.
- `DonationsPage.tsx`/`BookingsPage.tsx` (Phase 10b) — **read-only transactional ledgers**, not managed resources (staff can view/filter/sort but never create/edit/delete a donation or booking row directly). Built as standalone pages with a PrimeReact `DataTable` (server-side pagination via `page`/`limit`/`sortfield`/`direction` + flat `from`/`to`/`type`/`status` query params, mirroring `ExpenseTrackerPage.tsx`'s query shape) rather than forcing them through `CrudPage`, which assumes a form-editable resource.

### Year-wise filtering (`Admin/src/components/ui/YearFilter.tsx`, Phase 10b)

A small reusable `<YearFilter value={year} onChange={...} />` dropdown (+ `yearToDateRange(year)` helper) used on `DonationsPage`, `BookingsPage`, `ExpenseTrackerPage`, and the devotee `/devotee/bookings` page to quickly scope a list to a calendar year. On `CrudPage`-based screens it would compose via the `config.slots.toolbarRight` render-prop slot (which exposes `query`/`setQuery`); the pages that actually use it today are the bespoke ones above, where it just sets local `from`/`to` state.

### RTK Query (`Admin/src/services/api/apiSlice.ts`)

One `apiSlice` for the whole app. Every new API file must add its cache tag name(s) to this file's `tagTypes` array, or TypeScript will reject `providesTags`/`invalidatesTags` referencing that tag. **This is a single shared file — when building multiple features in parallel, add tags here once, centrally, at the end**, not per-feature, to avoid merge conflicts.

### i18n (`Admin/src/i18n/`)

**Staff and devotee language selection are fully independent** (Phase 13a) — `preferences.staffLocale`/`preferences.devoteeLocale` are two separate Redux fields (both persisted), each backed by its own hook: `useStaffTranslation()` / `useDevoteeTranslation()` (both thin wrappers over a private `useTranslationForAudience(audience)` in `useTranslation.ts`). `LanguageSwitcher.tsx` takes a required `audience: 'staff'|'devotee'` prop (it calls both hooks unconditionally — hooks can't be called conditionally — and picks by prop) and is mounted separately in the staff header/sidebar and in `DevoteeLayout`/devotee auth pages; changing one never touches the other, even when both are mounted at once (e.g. a staff member previewing the devotee site). `widgetRenderers.tsx` (Screen Customizer widget content) always uses `useDevoteeTranslation()` regardless of render context, since widget *content* is always devotee-facing.

For the 3 bundled locales (`en`/`te`/`hi`), `t(key)` resolves from the hand-written `Admin/src/i18n/translations/{en,te,hi}.ts` dictionaries instantly. For any other **enabled** locale (see the `language` module — up to 23 total), it lazily flattens the English dictionary (`flatten.ts`) and calls `POST /translations/:locale` once, caching the result in `preferences.dynamicTranslations` (persisted, shared across both audiences since the two namespaces never collide) so it's instant on every subsequent visit. `LanguageSwitcher.tsx` sources its option list from `GET /languages/enabled`.

**Two key namespaces**, disambiguated by whether the key contains a dot:
- **Dotted keys** (`staff.crud.search`, `login.brandName`, …) — hand-invented namespaced keys for shared chrome (the CRUD engine, login pages, common strings). Looked up by nested-path traversal.
- **Dot-free keys** (`t('Donors')`, `t('This will permanently delete {{name}}.')`) — a "content" key: the literal English string itself, used for the long tail of per-page titles/table-headers/form-labels across `Admin/src/models/*.tsx`/`Admin/src/pages/*.tsx` (Phase 13d). Internally rewritten to `content.<string>` and looked up in a `content` namespace added to each locale file; falls back to the **plain string itself** (not the dotted key) if no translation exists, so a not-yet-translated content string degrades to correct English rather than showing a raw key. `en.ts`'s `content` entries are self-mapped (key === value) specifically so the dynamic-translation pipeline picks them up and auto-translates them into any enabled non-bundled locale; `te.ts`/`hi.ts` carry real hand-written translations. This exists to avoid hand-inventing a namespaced key for every one of the 100+ per-page strings.

Since `models/*.tsx` files export plain consts/functions (not components — no hook access), a module converted for Phase 13d turns its exported table-columns/form-config/render-slot consts into **factory functions taking `t`** (e.g. `getDonorTableColumns(t)`), called from inside the corresponding `pages/*Page.tsx` component (which does have `useStaffTranslation()`) and wrapped in `useMemo(() => (...), [t])` so the whole `CrudPageConfig` re-derives when the staff language changes. See `models/donorModel.tsx` for the reference pattern this was standardized on. **Every staff module and page has now been converted this way** (Phase 13d, completed) — see `MEMORY.md`'s Phase 13 entry for the full list and the deliberate exceptions (Role's dynamic permissions matrix, Excel import/export column-matching keys).

**Backend locale propagation** (Phase 13b): `Admin/src/services/api/axiosInstance.ts`'s `attachLocaleHeader` interceptor derives the current audience from `window.location.pathname` (`/` and `/devotee/*` → devotee, else staff — same signal the router already uses) and reads the matching locale via `localeSessionBridge.ts` (a "read the Redux store from outside React" helper, same pattern as the pre-existing `authSessionBridge.ts`), attaching it as `Accept-Language`. `server/src/middlewares/locale.middleware.ts` negotiates against every currently-**enabled** `Language` (not a hardcoded 3-locale array), cached in-process for 60s.

### Screen customizer (`Admin/src/components/screenBuilder/`, `Admin/src/pages/ScreenBuilderPage.tsx`)

Staff-only drag-and-drop builder for the 10 devotee-facing screens (Home/Darshan/Seva/Accommodation/Prasadam/Donations/Facilities/Live/Events/Nearby Places). `BuilderCanvas.tsx` (react-grid-layout) handles drag/resize; `WidgetPalette.tsx` adds new widgets; `WidgetInspector.tsx` is the per-widget settings panel (per-language content tabs with an auto-translate-then-override flow, image upload via the existing `upload` module, carousel image-list/duration/transition controls). **Important design point**: the builder only customizes *presentational* zones — banners, carousels, promotional text/images, social links, announcement banners — mounted via `<ScreenRenderer screenKey="...">` at the top of each real devotee page. It does not touch the functional booking forms/tables themselves (those stay code-driven), so "customize the screen" can't accidentally break a booking flow.

**Preview (Phase 14a)**: `ScreenBuilderPage.tsx`'s Preview mode renders an `<iframe src="<real devotee route>?previewDraft=1">` — the actual real page (nav, footer, booking UI, everything), not an isolated widget tree. `ScreenRenderer.tsx` checks for that query param and fetches `draft` instead of `published` when present (staff-only endpoint; the iframe is same-origin so it shares `localStorage` and thus the staff session with the parent SPA). Toggling into preview auto-saves the draft first, so the iframe always reflects in-progress edits. The `SCREEN_PREVIEW_ROUTES` map (`Admin/src/types/pageContent.ts`) is the screenKey → real route lookup.

**Version history (Phase 14b)**: every **Publish** (not every draft save) snapshots the newly-published widget tree into `IPageContent.versions[]` (capped at 20). A "History" button opens a dialog listing past versions with a "Restore to draft" action — restoring copies that version's widgets into `draft` only, never overwrites `published` directly, so a restored version still goes through the normal Save → Preview → Publish review cycle. See `GET /page-content/:screenKey/versions` / `POST /page-content/:screenKey/versions/:versionId/restore`.

### Activity tracking & staff Analytics page (`Admin/src/utils/analytics.ts`, `Admin/src/pages/AnalyticsPage.tsx`)

`Admin/src/utils/analytics.ts` exports `trackPageview(path)` / `trackClick(path, label)` / `trackFunnelStep(path, funnelName, stepIndex, stepName)` — each just pushes onto an in-memory queue (session ID cached in `localStorage`), flushed every 10s or on tab-hide/unload via `navigator.sendBeacon` (falling back to a `keepalive: true` fetch), so tracking never blocks a click or a route change. `DevoteeLayout.tsx` calls `trackPageview` on every route change and `trackClick` on every nav-link click; `DevoteeDashboardPage.tsx`'s quick-action cards do the same. The 6 concrete funnels (darshan/seva/accommodation booking, prasadam order, donation, event registration) each fire a `viewed` step on page mount, a `submitted` step on booking success, and — where there's a natural single selection action — one step in between (e.g. `date_selected`, `stay_selected`, `fund_selected`, `item_added`). This is deliberately not a generic analytics SDK — the funnel names and step shapes are hardcoded to match `server/src/modules/analytics/analytics.constants.ts` exactly.

`AnalyticsPage.tsx` (staff, permission `analytics`) — built following the `dataviz` skill's procedure (form-before-color, the validated reference palette, hover tooltips, a legend-free single-hue treatment throughout since every chart here is a magnitude/trend job, not an identity job needing categorical colors). A 7/30/90-day range selector, a manual "Run rollup now" button (calls `POST /analytics/rollup/run` — useful for staff to force a refresh without waiting for the nightly cron), then: 3 stat tiles (visits today, total visits in range, features-used ratio), a daily-visits line chart, top-pages and top-clicked-features horizontal bar charts, a small-multiples grid of per-funnel drop-off bar charts (one mini chart per funnel, since 6 similar series is exactly the case small multiples are for), and a used-vs-never-used feature list with a status dot (never color-alone — the row also says "Used"/"Not used yet" in text).

### Devotional visual theme

The devotee portal (`Admin/src/features/devotee/styles/devoteePortal.css`, `Admin/src/features/auth/styles/templeLogin.css`) defines the maroon/gold/parchment palette (`--dp-maroon`, `--dp-gold`, `--dp-bg`, fonts `Cinzel`/`Mukta`/`Yatra One`). ## Data flow example — a devotee books a seva

1. `DevoteeSevaPage.tsx` calls `useCreateSevaBookingMutation()` → `POST /seva-bookings`.
2. `seva.controller.ts` → `seva.service.ts`'s `createBooking`: creates a `SevaBooking` doc, then calls `bookingService.createLedgerEntry({type:'seva', refId: booking._id, ...})`.
3. The devotee's `/devotee/bookings` page (and the ledger) now shows it via `GET /bookings`.
4. Cancelling calls `POST /bookings/:id/cancel` → the ledger looks up the `seva` cancel handler (registered by `seva.service.ts` at import time) → flips the underlying `SevaBooking.status`, then flips the ledger row's status.

## Payments (Phase 15 — direct UPI, no gateway)

`TempleProfile.upiId` (the temple's own VPA) + `server/src/utils/upi.util.ts` (mirrored client-side in `Admin/src/utils/upi.ts`) build a standard `upi://pay?pa=...&pn=...&am=...&cu=INR&tn=...` deep link — opens the devotee's own UPI app for a direct bank-to-bank transfer, no gateway/API keys. `Admin/src/features/devotee/components/UpiPaymentPanel.tsx` renders this as a QR code (`qrcode` npm package) + "Pay Now" link + an optional "I've paid, enter UTR" field, shown on all 5 booking/donation devotee pages whenever the created record's `amount > 0`.

There's no gateway webhook, so this plugs into the pre-existing manual-reconciliation model: `Booking.paymentReference`/`Donation.paymentReference` (new optional fields) hold the devotee-self-reported UTR. `PATCH /bookings/by-ref/:refId/payment-reference` is **public** (no auth) — looked up by `refId` (the domain doc's own `_id`, already known to the frontend right after creation), specifically so guest checkout (which has no session — even `cancel`/`receipt` require auth) can still self-report a reference. Staff then confirm it against the bank statement and call `PATCH /bookings/:id/mark-paid` (`BookingsPage.tsx`) or `PATCH /donations/:id/mark-paid` (`DonationsPage.tsx`) — both staff-only (`Update` action on `bookingLedger`/`donation` permission keys).

**Known quirk**: a donation writes to *two* places — its own `Donation` doc and a mirrored row in the shared `Booking` ledger (`type: 'donation'`) — a donation's `paymentStatus`/`paymentReference` are **not cross-synced** between the two. Marking a donation paid via `DonationsPage.tsx` does not update its mirrored ledger row (and vice versa via `BookingsPage.tsx`). This is pre-existing redundancy in how donations were modeled (not introduced by Phase 15), called out here rather than silently left inconsistent.

## Notifications (email + WhatsApp)

Every booking/order/donation/event-registration creation path fires two independent, fire-and-forget confirmations right after the ledger entry is written — neither can ever fail the booking itself:
- `server/src/services/notification/bookingEmail.service.ts` (Phase 7) — HTML email via `nodemailer`, only sent when a `contactEmail` is present.
- `server/src/services/notification/whatsapp.service.ts` (Phase 16) — plain REST call to Meta's WhatsApp Cloud API (no SDK, no Twilio), only sent when a `contactPhone` is present (`ResolvedBooker.contactPhone`, populated the same way as `contactEmail` — `user.phone` for logged-in devotees, `guestPhone` for guests). This is what finally delivers a confirmation to phone-only guests, who previously got none at all.
- Meta requires an **approved message template** for any business-initiated message like a booking confirmation (free-form text only works as a reply within a 24h customer-service window, which doesn't apply here). Until the temple has its own approved template, `WHATSAPP_TEMPLATE_NAME` defaults to Meta's zero-parameter `hello_world` demo template — real booking details (temple name, type, date, amount, reference) are fully wired to send the moment a real template is approved and configured; no code changes needed, just the `.env` vars.
- Both are `.env`-configured and entirely optional — an unconfigured install just logs and skips (`WHATSAPP_PHONE_NUMBER_ID`/`WHATSAPP_ACCESS_TOKEN` blank → skip; mail send failure → caught and logged).

## Known limitations (intentional, by scope decision)

- **No payment gateway** (by explicit user choice — see Payments section above for what direct-UPI does instead). Donation/seva/prasadam records still use the same `paymentStatus` field (`pending|paid|waived`) for reconciliation; the UPI panel just gives staff a self-reported reference to check against the bank statement instead of purely counter/cash reconciliation.
- **No persistent guest identity.** A guest booking captures contact info per-transaction (for the confirmation email) but there's no session/account — no "my bookings" for guests, by design (see the guest-checkout answer in `MEMORY.md`).
- **No SMS delivery** — but this is superseded by Phase 16: a phone-only guest now receives a WhatsApp confirmation instead (see Notifications section above), so the practical gap is closed even though literal SMS was never implemented.
- **Translation quality depends on what's actually running.** LibreTranslate and/or Ollama must be running (see `.env`'s `LIBRETRANSLATE_URL`/`LLM_BASE_URL`) for real translations; if neither is reachable, every "translation" silently passes through the original English text rather than erroring — check `TranslationCache` in Mongo to see whether real translation is happening.
- Catalog list endpoints (seva/darshan/accommodation/prasadam/donation-fund/facility/temple-events/nearby-places) return unpaginated flat arrays and only active items — fine at temple-catalog scale, would need real pagination if a catalog grows very large.
- The screen customizer's "invoice/ticket" and announcement images are simple URLs, not generated PDFs — flagged as a possible future add, not built.
- **Booking-open-time display is informational only, not enforced (Phase 10e).** `bookingOpensAt`/`bookingClosesAt` on the 4 catalog models render as a "Bookings open X – Y" note on the devotee page; nothing on the server rejects a booking made outside that window. Enforcing it would be a deliberate follow-up, not an oversight.
- **This is a single-reconfigurable-instance app, not multi-tenant SaaS.** One deployment = one temple's data. A second temple means a second deployment, each independently reconfigured — there's no tenant-isolation/shared-DB-multiple-temples architecture. Phase 11 built the reconfigure tooling for the *within-one-deployment* rebrand case (see `templeReconfigure` in the module table and `Admin/src/pages/ReconfigureTemplePage.tsx`); it does not turn this into multi-tenant SaaS.
- **The reconfigure wizard can't reach every hardcoded temple-specific string.** Phase 11's audit pass fixed the ones that mattered most (staff login brand name, devotee header/hero/footer — all now read `TempleProfile.templeName` with the old hardcoded string only as a fallback if the profile fetch hasn't resolved yet). **Left deliberately alone**: `login.eyebrow`/`devotee.eyebrow`'s Sanskrit deity invocation ("|| Om Sri Gudavalamma Devi Namaha ||") — genuinely temple-specific religious content with no generic `TempleProfile` field to hold it, and out of scope for an automated per-temple swap (a real re-skin would need this line hand-edited in the i18n dictionaries, or a new profile field added, which wasn't asked for). Also left alone: `TempleProfile.model.ts`'s Mongoose-schema-level `default: 'Gudavalamma Temple'` on `templeName` — harmless (never actually used, since `templeProfileService.getOrCreate()` always sets `templeName` explicitly on first creation) but technically still a hardcoded string in the schema definition.
- **Analytics (Phase 12) tracks 6 concrete funnels and a fixed list of ~20 click targets, not every possible interaction.** Adding tracking to a new page/button is a manual `trackPageview`/`trackClick`/`trackFunnelStep` call, not automatic instrumentation. Funnel drop-off and feature-usage counts are **distinct-session** counts (a session that repeats a step only counts once), which is usually what you want for drop-off but means the raw `AnalyticsEvent` count for a step can be higher than the funnel chart's number.
- **The analytics rollup only pre-aggregates one metric family (visits/sessions) into `AnalyticsDailyRollup`.** Top pages, top clicks, and funnel drop-off are computed live from raw `AnalyticsEvent` on every `GET /analytics/summary` call (bounded by the selected day range, default 30). Fine at temple-site traffic scale; would need its own rollup fields if traffic grew enough for that live aggregation to become slow.

## Demo data (Phase 20)

`server/src/scripts/seed-demo-data.ts` populates every temple-management screen with realistic, cross-linked data (donors, properties, assets, liabilities, donations, all 4 booking types, temple events, announcements, the expense tracker, and 21 days of analytics events + daily rollups) — built specifically so the platform demos coherently for a government/Minister-of-Parliament audience rather than showing empty tables. It inserts directly via Mongoose rather than the real HTTP/service layer (to avoid firing ~90 real email/WhatsApp sends at fabricated addresses), but mirrors each service's exact domain-doc + `Booking`-ledger shape (title format, `refModel`, ledger-date convention) so the seeded rows are indistinguishable from ones the real app would create. Guarded to abort if `Donor` documents already exist, so it's safe to leave in the repo and re-run defensively. See `MEMORY.md`'s Phase 20 entry for the full inventory of what it creates.
