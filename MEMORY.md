# Project Memory / Build Log

Purpose: a running record of what's been built, why, and what's left — so a future session (human or LLM) doesn't have to re-derive it from git history or by re-reading the whole codebase. Update this file when you complete a phase of work, not after every commit.

## Starting point (before this build-out)

- Repo was a merged/repurposed template: `server/src/modules` and `Admin/src/pages` contained ~150 files of an unrelated healthcare RCM app, a mining-equipment AI app, a social-media publishing suite, and a deployment/infra self-healing suite.
- One commit ("trail temple pages") had added the entire devotee-facing UI (login/register/dashboard/darshan/seva/accommodation/prasadam/donation/live/bookings/facilities/profile) as **pure frontend mocks** — hardcoded data, toast-only actions, nothing persisted.
- No i18n system was app-wide (two separate hand-rolled contexts, login-only and devotee-only).
- No LLM config existed for the temple app specifically.
- Login credentials: `admin@yopmail.com` / `Emp1234$` (Super Admin), seeded in MongoDB database `templateDb` on `mongodb://localhost:27017`. (Note the DB name is `templateDb`, not `templeDb` — a real bug that broke login once during this project; the `.env`/`.env.example` `MONGO_URI` must point to `templateDb`.)

**Mid-phase: fixed a live crash unrelated to the current feature.** The user hit `Cannot read properties of undefined (reading 'kn')` in `useTranslation.ts` while browsing with Kannada (`kn`) selected — a non-bundled locale. Root cause: `redux-persist`'s root-level `persistReducer` (wrapping `combineReducers`, whitelisting `preferences` among other slices) replaces the *entire* `preferences` object from localStorage on rehydration rather than deep-merging it with the reducer's `initialState`; a browser session with `preferences` persisted from before `dynamicTranslations` was added to the slice (Phase 6) rehydrates with that key genuinely absent, not just empty. Both crash sites — the `t()` function and the `useEffect` that lazy-fetches a dynamic locale's dictionary — read `dynamicTranslations[language]` without a guard. Fixed by defaulting the selector to `{}` in `useTranslation.ts` and defensively initializing `state.dynamicTranslations` inside the `setDynamicTranslations` reducer in `preferencesSlice.ts` (belt-and-suspenders — either fix alone would have resolved the report, both together close the same root cause at both read and write sites). **Not fixed, and out of scope for this patch**: the general class of bug (any `preferences` field added after a user's first session could theoretically be missing the same way) — a proper fix would be a `redux-persist` migration or switching the reconciler; flagged here rather than silently left for the next person to rediscover.

**Also mid-phase**: running `npm install node-cron@4.5.0` in `server/` triggered `npm` to reconcile `package.json`/`package-lock.json` against the actual dependency tree, which surfaced (and completed) an already-pending-but-uncommitted cleanup from Phase 0: `googleapis`, `iplocation`, `pdf-lib`, `randomstring`, `socket.io`, `ssh2` (and their `@types/*` counterparts) and several RCM-specific npm scripts (`seed:rcm-*`, `rcm:*`) were still listed in `package.json` despite their source files having been deleted back in Phase 0 — package.json itself was never updated to match. This was **pre-existing uncommitted working-tree state**, not something this session's edits caused; verified safe by confirming `npm run build` still passed cleanly (it always had, throughout Phases 10–11, which is only possible if none of that code was actually depended on). Called out here in case the size of that diff is surprising in a future `git diff`.

**Phase 13 — Multilingual completion (staff + devotee, fully independent language selection).** Built to satisfy live browser-testing feedback: menu headings and staff-side content were almost entirely hardcoded English, and switching language as staff shouldn't affect the devotee-facing language (or vice versa). **User's explicit correction, standing for all future integration work this session**: any paid integration proposal (payment gateway, WhatsApp provider) must be replaced with a free alternative — see Phases 15–16 below.

- **13a — Independent locale state.** `preferencesSlice`'s single `locale` field replaced with `staffLocale`/`devoteeLocale` (both default `'en'`). `useTranslation.ts` rewritten: a private `useTranslationForAudience('staff'|'devotee')` backs two public hooks, `useStaffTranslation()`/`useDevoteeTranslation()`, each reading/writing only its own field — switching one can never touch the other, even when both are mounted at once (e.g. staff previewing the devotee site). `LanguageSwitcher.tsx` takes a required `audience` prop (calls both hooks unconditionally — React's rules of hooks forbid calling one conditionally — and picks by prop). `widgetRenderers.tsx`'s `useWidgetText` deliberately always uses `useDevoteeTranslation()` regardless of render context, since widget *content* is always devotee-facing even when being edited/previewed from the staff side.
- **13b — Backend locale propagation (the actual "menu headings don't translate" root cause).** No axios call anywhere ever attached a locale header, and `server/src/app.ts`'s negotiation middleware was hardcoded to only `en`/`te`/`hi`. Fixed: new `localeSessionBridge.ts` (same "read the Redux store from outside React" pattern as the pre-existing `authSessionBridge.ts`) + an axios request interceptor (`attachLocaleHeader`) deriving audience from `window.location.pathname` and attaching the right `staffLocale`/`devoteeLocale` as `Accept-Language`. New `server/src/middlewares/locale.middleware.ts` negotiates against every currently-*enabled* `Language` (up to 23, 60s in-process cache), not a hardcoded 3-locale array. This alone made the pre-existing (Phase 6) per-request menu-title translation actually reachable from the in-app switcher.
- **13c — Shared CRUD engine chrome.** New `staff.crud` i18n namespace (~53 hand-translated keys: Search/Add/Edit/Delete/Save/Cancel, dialog titles, confirmation messages, filter-operator labels, paginator template) wired into `CrudPage.tsx`/`CommonTable.tsx`/`CommonForm.tsx` via `useStaffTranslation()`. Several module-scope helpers that don't have hook access (`withCreatedColumn`, `inferMarkedColumnFilter`, `withMarkedFilters`, the filter-match-mode label arrays in `CommonTable.tsx`) were parameterized to take already-translated strings/`t` instead. **Incidental bug fixed while here**: `CommonTable.tsx`'s row-action button styling (`getActionButtonClassName`) inferred edit/view/delete color-coding by substring-matching the (now-translatable) English label text — this would have silently broken (all actions rendering the same neutral color) in any non-English locale. **Post-Phase-19 bugfix — locale silently reset to English on every refresh.** The user reported: "on refresh it is showing telugu and coming back to english immediately." ## Incidents / things to watch for

- **A background agent testing the API reset the real `admin@yopmail.com` password** by running `server/src/scripts/list-users.ts` (which hard-codes a password reset to `Admin@123` when executed) to obtain a bearer token for live testing. Fixed by resetting the password back to `Emp1234$` through the actual Mongoose model (so salt/hash stay consistent). **Lesson: never run `list-users.ts` against a real/shared dev database to "get a token" — it mutates the admin account's password as a side effect.** Use a disposable test user instead.
- Icon names used in `menu.seed.ts` must exist in `Admin/src/utils/menuIcons.ts`'s `menuIconMap`, or they silently render as a plain circle. Check that file before inventing a new `iconName`.
- The dev server (`npm run dev` in `server/`) does not auto-restart cleanly across long idle gaps in some environments — if API calls start returning connection errors, check `lsof -i :5005` and restart with `npm run dev` if nothing is listening.
- **`react-grid-layout`'s latest major (v2.x) has a completely different, hooks-based API** (`GridLayout`/`ReactGridLayout` with `width`/`gridConfig`/`layout` props, no `WidthProvider`/`data-grid` children pattern). If `npm install react-grid-layout` without a version pin, you'll get v2 — pin to `1.5.4` (or check what's actually in `package.json` before assuming the classic API) unless you deliberately intend to learn/use the v2 API.
- Every new backend module needs its permission key added to `server/src/constants/roles.constants.ts` AND its route mounted in `server/src/routes/index.ts` AND (if it has translatable messages) registered in `server/src/i18n/index.ts` — this was already flagged once (see the Phase 3 gap above) and remains the single easiest thing to forget when adding a module by hand.
- **`generateListQuery`'s default filter silently zeroes out results on models without an `active` field.** It always seeds `{isDeleted: {$ne: true}, active: true}`. Ledger-style models (`Booking`, `Donation`) don't have soft-delete/`active` fields at all — `active: true` then matches nothing, since every document's `active` is `undefined`. Fix: `delete query.filter.active; delete query.filter.isDeleted;` right after calling `generateListQuery`, before merging in your own filters (see `donation.controller.ts#list` / `booking.controller.ts#listAll`). Found while building the Phase 10b staff ledgers — the `activity` module's `getActivities` has the same latent bug (never cleaned up, pre-dates this session's work; the activity log likely already returns zero rows in production, not something introduced here).
- **Never test a destructive endpoint (bulk delete/reset/overwrite) directly against real, already-populated collections in the shared dev database, even via a "safe" direct-service script.** For Phase 11's catalog-reset wizard, the correct pattern was: read-only query first to confirm the target collection's exact current content (and that it's low-value/reproducible, e.g. still exactly the seed defaults), snapshot it in memory, run the destructive operation, verify the result, then restore the *exact* original documents (same `_id`s) before the script exits — never assume "I'll just re-seed after" is equivalent to "I put back what was actually there." Apply the same discipline to any future phase that adds a bulk-delete/reset/overwrite feature (e.g. Phase 14's hotel-listing management, Phase 13's social-post scheduling).
- **A new field added to a `redux-persist`-whitelisted slice can be `undefined` at runtime for any browser session that persisted state before the field existed** — the root-level `persistReducer` here replaces a whitelisted slice's state wholesale from localStorage rather than deep-merging with `initialState`. Any code reading a `preferences.*` (or `auth.*`/`session.*`) field added after early sessions began must either default it at the selector (`useAppSelector(...) ?? fallback`) or guard the reducer that writes it. Confirmed to have actually bitten `preferences.dynamicTranslations` (added in Phase 6, crashed in Phase 12) — the same risk applies to any other field added to that slice since its first use.
- The seed script (`npm run seed`) is **not** run automatically on server start — it's a standalone script (`server/src/database/seeds/index.ts`) that connects, seeds, and exits. Any change to `roles.constants.ts` (new permission key) or `menu.seed.ts` (new menu entry) needs an explicit `npm run seed` re-run before it takes effect against a running dev instance; the dev server itself doesn't need restarting for route/permission changes (ts-node-dev already does that on file save) but the DB-side role/menu documents won't update themselves.
